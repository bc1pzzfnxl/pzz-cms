# Template vs deployment

`pzz-cms` is the **upstream template**. `bc1pzzfnxl-blog` is a **deployment** of
that template. The two repositories share most of their code, but not their
identity, their Cloudflare resources or their content.

Never copy a deployment-specific file back into the template.

## What is shared

These files are code, and changes flow from `pzz-cms` to the deployment:

- `apps/site/**` (public pages, layout, middleware, styles, astro config)
- `packages/core/**` (content module, helpers, MDX components)
- `tests/**`, `scripts/**`, `migrations/**`
- `package.json`, `bun.lock`, `vitest.config.ts`, `playwright.config.ts`,
  `biome.json`, `tsconfig.json`
- `docs/**`, `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md`, `PLAN.md`

Never sync `apps/cms/**`: the admin is local-only and lives in the template
repository alone.

## What belongs to the deployment

Never copy these from the template into a real site, or from a site into the
template:

| File | Why |
| --- | --- |
| `packages/core/src/lib/site.ts` | Name, canonical URL, description, author, logo, default cover |
| `apps/site/wrangler.jsonc` / `apps/cms/wrangler.jsonc` | Real D1 database id, R2 bucket, Worker name (the deployment only carries the site one) |
| `.dev.vars`, `.env*` | Secrets (`BETTER_AUTH_SECRET`, `SETUP_TOKEN`, owner email) |
| `public/favicon*`, `public/apple-touch-icon.png`, `public/images/*` | Branding and site assets |
| D1 rows and R2 objects | Articles, documents, categories, media |
| `content/` | The Git mirror of the deployment's articles; never committed in the template |
| `migration-output/` | Private imported content, gitignored |

`packages/core/src/lib/site.ts` is the **single source** of the site URL:
the site `astro.config.mjs`, `robots.txt`, `llms.txt`, the sitemap, RSS and
JSON-LD all read it. `public/`
must not contain a hardcoded `robots.txt` or `llms.txt`; those are generated by
`src/pages/robots.txt.ts` and `src/pages/llms.txt.ts`.

## Sync procedure

1. Make the change in `pzz-cms`, on a `feat/…`, `fix/…` or `chore/…` branch.
2. Run `bun run check`, `bun run build:site` and `bun run build:cms` there;
   let CI pass.
3. Copy only the shared files listed above into the deployment (never
   `apps/cms`).
4. Check the deployment diff: it must not contain `site.ts`, Wrangler config,
   secrets, content or generated assets.
5. Run `bun run check` and `bun run build:site` in the deployment, push, let
   Workers Builds pass, then deploy.
6. Deploy with the deployment's own `apps/site/wrangler.jsonc` (real IDs,
   gitignored); never commit it.

## Content mirror

The deployment keeps a text mirror of D1 in `content/`:

```bash
bun run content:sync -- --config=apps/site/wrangler.jsonc
bun run content:import -- --config=apps/site/wrangler.jsonc
bun run media:gc -- --bucket=<r2-bucket> --config=apps/site/wrangler.jsonc
```

- `content:sync` writes one `.mdx` per article plus `categories.json`,
  `media.json` and `manifest.json`. The deployment repository is private, so
  use `--all` to include drafts; the default mirrors published articles only.
- `content:import` recompiles MDX and upserts the mirror into D1. It restores
  text and media metadata, not the R2 objects: images must still exist.
- `media:gc` deletes media rows and R2 objects that no current article or
  document references, after 7 days by default.
- The template never commits `content/`; only the deployment does.
- Images are never mirrored. Deleting a replaced image also breaks the old Git
  versions that referenced it; that is the accepted cost of staying inside the
  R2 free tier.
- Restore and Time Travel procedures live in
  [`docs/backup.md`](./backup.md). Run the local restore drill after changing
  the mirror format.

## Current gaps

- The `shadcn` CLI is a dev dependency of `apps/cms` because the admin CSS
  imports `shadcn/tailwind.css`.
- The admin (`apps/cms`) does not exist in the deployment repository; local
  edits require cloning the template too, or keeping the deployment's copy of
  the CMS config alongside.
